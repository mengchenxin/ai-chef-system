二、 Day 1 核心：智能体的推理与决策机制

面试官最关心的首要问题：你是否理解 Agent 是如何思考和行动的？本节通过交互式选项卡，详细拆解了工业界最常用的三种推理策略。点击下方标签页探索不同的工作流机制。

🔄 ReAct (Reason + Act) 基础运行逻辑

工业界最基础的 Agent 运行逻辑。大模型不能直接执行动作，必须先输出思考过程。在 Node.js 中，这本质上是一个被代码控制的 while 循环状态机。

1. Thought (思考)
模型分析现状，决定下一步动作。
➔
⬇
2. Action (行动)
模型输出需要调用的工具和参数。
➔
⬇
3. Observation (观察)
Node.js 执行工具后，返回结果给模型。

📋 Plan-and-Solve (计划与解决)

针对宏大或复杂任务的策略。核心动作是**任务拆解 (Task Decomposition)**。

阶段一：大模型 Planner

让大模型作为 Planner，输出包含多个子任务的结构化 JSON 数组。

[ {"step": 1, "task": "搜索相关资料"}, {"step": 2, "task": "提取关键数据"} ]
阶段二：Node.js Executor

Node.js 作为 Executor，维护一个任务队列，调度底层的 Worker Agent 逐一执行子任务，汇总结果。

🛡️ Self-Reflection (自我反思与纠错)

区分玩具项目与工业级系统的关键：为 Agent 添加系统级异常捕获机制。应对外部 API 崩溃、工具调用超时、大模型参数解析失败等痛点。

兜底策略 (Node.js 层面)

绝对不要将错误直接抛给用户。Node.js 捕获异常后，将错误信息（Error Stack）或自定义提示词封装成 Observation，附加“执行失败，请分析原因并重试”的指令，再次提交给大模型，触发其自我纠正。

三、 Day 2 核心：工具调用 (Tool Calling) 极致工程化

如果说 ReAct 是 Agent 的大脑，那么 Tool Calling 及其背后的 JSON Schema 就是 Agent 的手脚和数据契约。本节包含了概念对比、代码结构解析以及一个交互式错误诊断器，帮助您理解如何处理模型约束失败的情况。

Prompt (提示词)

给大模型“洗脑”的自然语言，决定模型怎么思考。它是灵活的、逻辑驱动的。

2.2 防御体系：格式幻觉与基石组件

如何彻底解决大模型不按套路出牌的“格式幻觉”？你需要理解 API、校验库等基础设施，并构建坚不可摧的三道防线。

🏗️ 基础设施生动隐喻

💁‍♂️ API (接口) = 餐厅服务员

不同系统间传递数据的小哥。你（Node.js）不能直闯大模型机房，只能把需求交给服务员（大模型 API）；大模型要做事，也要让服务员（外部 API）去跑腿获取外部信息。

🛡️ 数据校验库 (如 Zod) = 夜店严厉保安

守在 Node.js 核心代码门口的保安。大模型传回的数据如果不符合要求（如要求数字14却给了汉字“十四”），Zod 会立刻拦截并抛出精准的报错原因，绝不让脏数据搞崩后端系统。

🧋 Enum (枚举) = 奶茶甜度单选框

限定取值范围（如 ["celsius", "fahrenheit"]）。就像奶茶店的下拉菜单，不让大模型随性发挥填“摄氏”或“度”，从源头掐断捏造数据的格式幻觉。

🦠 击溃“格式幻觉”的三道防线

格式幻觉主要包括：类型叛逆(字串当数字)、偷工减料(漏字段)、无视边界(瞎编枚举)。解决它们需要组合拳：

第一道防线：Prompt 级软约束 (示范)

在 System Prompt 里直接给大模型贴一个标准 JSON 答案示例（Few-Shot）。大模型是模仿大师，看到例子就不容易发散错误。

第二道防线：Schema 级硬约束 (锁死)

利用 Enum 和 Required 字段锁死选项范围。结合目前最新 API 提供的 strict: true (结构化输出模式)，在底层物理层面上限制大模型乱吐 Token。

第三道防线：Zod 拦截 + 自我反思 (兜底)

Node.js 收到数据后先交由 Zod 校验。一旦校验失败捕获异常，将报错信息打包成 Observation 发回给大模型：“格式有误，缺少必填字段X，请修正重试。”强制其自我纠错。

四、 Day 3 核心：工作流引擎与编排 (Orchestration & DAG)

当业务变得极其复杂时，单个 while 循环已经无法驾驭。我们需要脱离单纯的 Prompt 工程，引入“图（Graph）”和“状态机（State Machine）”的概念，也就是用代码手写 Dify/Coze 里的连线逻辑。

1. 告别单体循环，拥抱 DAG

DAG (有向无环图) 允许我们将复杂的任务拆分成一个个独立的节点 (Nodes)。每个节点只负责一件小事（比如只负责查数据库，或只负责总结）。节点之间的箭头 (Edges) 决定了执行的流向。

2. 三大核心基石 (类 LangGraph 思想)

  • 📦 State (状态): 这是一个全局的 JSON 对象。它像一个流水线上的篮子，每个节点都可以往里面放东西或修改东西。
  • ⚙️ Nodes (节点): 执行具体任务的函数。比如“意图识别节点”、“天气工具节点”。它们接收 State，执行完后更新 State。
  • 🔀 Edges (边/条件): Node.js 里的 if/else 路由，根据当前的 State 决定下一个该去哪个节点。

🧺 深入拆解：State（篮子）到底是怎么流转的？

节点（Node）之间是不允许直接互相调用和传参的！它们只能和中央的 State 篮子进行交互。这就是数据解耦的魅力。

1
起点 (Start) 投入问题

用户提问“北京今天热吗？”。引擎创建一个空的 State 篮子，把纸条 input: "北京今天热吗？" 扔进去。

2
Router (意图识别节点) 添加意图

Router 节点拿到篮子，看了看纸条，判断这是查天气。它往篮子里塞入新纸条 intent: "weather"，然后把篮子放回传送带。

传送带代码(Edge)检查篮子：发现 intent === 'weather'，把篮子运给 Weather Tool。
3
Weather Tool (工具节点) 添加结果

工具节点拿到篮子，调用真正的天气 API 查到了 35 度。它往篮子里塞入纸条 tool_result: "35度"。

4
Summarize (总结节点) 输出最终答案

总结节点拿到篮子，看到里面有所有线索。它生成并放入最后一张纸条 final_answer: "今天北京35度，很热"。流程结束。

🕸️ 业界风向标：到底什么是 LangGraph？

我们在上面讲的这套“图 (Graph) + 状态篮子 (State)” 的架构，正是目前业界最火的 Agent 框架 LangGraph 的核心设计哲学。

背景痛点

以前大家用 LangChain 的时候，发现它是直线运行的管道（Chains），没法很好地处理大模型需要反复思考、纠错的“死循环”问题。一出错就全盘崩溃。

LangGraph 的诞生

LangChain 团队开发了 LangGraph，它是一个专门用来构建“有状态的、多参与者”大模型应用的库。它帮你把“节点、边、状态流转”在底层封装好了，你只需要往里面填业务代码即可。

⚖️ 架构对比：为什么高级 Agent 必须用状态机？

📦 传统 Node.js 接口 (黑盒直写)
执行方式:

巨大的嵌套函数，代码从上跑到底。如果中间调 API 失败，整个请求直接挂掉 (500 Error)。

数据传递:

局部变量通过函数参数层层传递 (funcA(data) -> funcB(data))。执行到一半很难知道全局状态。

长程任务:

无法暂停。如果遇到需要“等待人工确认”的节点，传统 HTTP 请求会直接超时。

🕸️ DAG 状态机引擎 (白盒流转)
可观测性:

每个 Node 独立。引擎可以精确定位哪个节点报错，并仅对该节点进行重试，系统极具鲁棒性。

全局可见:

所有节点从统一的 Global State 读写数据。随时可以把整个 State 打印出来或存入数据库进行快照备份。

可中断/恢复:

因为有了 State 快照，流程可以随时暂停（断点挂起），明天读取 State 扔进引擎即可继续无缝执行 (Human-in-the-loop)。
