🧠 Day 6 记忆架构与并发

拯救大模型的“失忆症”

大模型和 HTTP 一样是无状态的。我们必须用工程手段构建多层记忆中枢。

工程化三大记忆流派

1. 临时会话记忆

类比：内存 (RAM)

死记硬背最近几轮对话，全量发送。痛点：聊得越多 Token 消耗呈指数爆炸，易超出模型容量。

2. 滚动摘要记忆

类比：追剧“前情提要”

超载后后台唤醒模型，将前几十条废话精炼成 200 字摘要。只发摘要+最新两句话，极限压缩 Token 成本。

3. 语义长期记忆

类比：硬盘 / 档案柜

异步提取用户画像存入向量库。下次登录捞取，实现跨月/跨周期的个性化记忆唤醒。

🎢 游乐场比喻：秒懂 Cookie、Session 与 Redis

既然要存记忆，存哪最安全？存哪不串线？

🎫

1. Cookie：装在口袋里的纸质门票

存在你的电脑（客户端）里。每次发请求自动带上。但极其不安全，谁捡到门票/篡改名字，就能冒充你。所以绝对不能存聊天记录等机密。

🗄️

2. Session：服务台内部的档案柜

你只有一张带编号的手环(SessionID存在Cookie里)。你的真实聊天记录存在服务器内存的档案柜里，很安全！
痛点：游乐场太大了有 10 个 Node.js 服务器。A 机器的档案柜，B 机器查不到！而且 Node.js 一重启，内存档案全没。

🚀

3. Redis：全场联网的高速中央储物柜

所有 Node.js 服务器都不存记忆。全部拿着你的 SessionID，去这台超级快的中央数据库（Redis）里读写。这完美解决了分布式架构的共享和持久化问题。

🔥 面试必杀技：高并发隔离防串线

在单线程的 Node.js 中，用全局变量 let history=[] 会导致 1 万用户的聊天记录互串，造成灾难性泄露。

“在分布式后端中，Agent 必须遵循无状态设计 (Stateless)。我们绝不在进程内存中存记忆，而是采用 Redis 缓存 + Session 隔离机制：

当请求进入 DAG 状态机引擎时，系统在入口节点（Start Node）根据唯一的 sessionId 异步读取 Redis 中的记忆，并注入到本次执行流的 Global State 篮子 中。在出口节点（End Node）结束时，将更新后的 State 同步覆盖回 Redis。这彻底杜绝了并发串线，且保障了后端的水平扩容能力。”
